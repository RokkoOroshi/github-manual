## 概要
gitとは簡潔に言えば**バージョン管理システム**である。主な利点を述べると
* 変更履歴が残せて、ロールバックが簡単にできる。
* ブランチによって、試作品をある時点からの完成品から簡単に分岐できる。
* 共同作業がしやすい。
今の時点ですべて理解している必要はないが、覚えておいてほしい。

## organizationアカウントとは
GitHubには個人アカウントとは別に、**organizationアカウント**（組織アカウント）という仕組みがある。
部やチーム単位でリポジトリをまとめて管理できるのが特徴で、メンバーの権限管理もここで行う。

個人アカウントとの主な違いは以下の通り。
| | 個人アカウント | organizationアカウント |
|---|---|---|
| 所有者 | 個人 | チーム・組織 |
| リポジトリ | 個人の作業用 | チーム共有のプロジェクト |
| メンバー管理 | なし | 招待・権限設定が可能 |

### メンバーとして使う場合に変わること
個人リポジトリと操作自体は同じだが、以下の点が異なる。

**リポジトリのURL形式が違う**
個人リポジトリは `github.com/[自分のユーザー名]/[リポジトリ名]` だが、
organizationのリポジトリは `github.com/[organization名]/[リポジトリ名]` になる。
cloneする際はこのURLを使う。

**mainブランチに直接pushできない場合がある**
organizationでは「ブランチ保護ルール」を設定できる。
これが有効になっているリポジトリでは、mainブランチへの直接pushが禁止されており、
必ずブランチを切ってPull Requestを経由してmergeする必要がある。

**Pull Requestにレビューが必要な場合がある**
organizationのルール次第では、他のメンバーの承認（レビュー）がないとmergeできない設定になっていることがある。
勝手にmergeできないのは仕様なので、レビュアーに確認を依頼すること。

部のリポジトリはorganizationアカウント配下にあるため、作業を始める前に管理者から招待を受ける必要がある。
招待はGitHubに登録したメールアドレス宛に届くので、承認してから初期設定に進むこと。

## 初期設定
### gitのインストール
1. 「win + R」でファイル名を指定して実行を起動して[pwsh]と打ち込んでpowershellを実行
1. powershellにて
    ```
    winget install Git.Git
    ```
    を打ち込んでインストーラを起動
    インストーラの質問はすべてYESでよく、初期セットアップのままインストールしてよい。
### githubの設定
1. まず、githubにてアカウントを作る。
    名前は一旦本名でも良いし、そうでなくてもよい。
1. その後、部の組織アカウントに招待してもらう。

## 使い方
### 基本的な流れ
実際の作業は以下の順番で行う。
```
clone → branch → ファイルを編集 → commit → push → Pull Request
```
最初だけcloneが必要で、2回目以降は branch から始める。
各コマンドの詳細は以下を参照。

### コマンド詳細
1. ディレクトリ移動
    powershellを起動し
    ```
    cd [移動したいディレクトリへのpath]
    ```
    > ※ `../` などの相対pathも覚えると便利

1. clone
    * コマンド
        ```
        git clone [リポジトリのURL]
        cd [リポジトリ名]
        ```
    * 使い方
        GitHubのリポジトリページを開き、「Code」ボタンをクリックしてURLをコピーする。
        powershellで作業したいディレクトリに移動した後、上記コマンドを実行する。
        cloneが完了するとリポジトリ名のフォルダが作成されるので、`cd`で中に入る。
    * 概要
        リモートリポジトリ（GitHub上のデータ）をローカル（自分のPC）にコピーすること。
        基本的に最初に一度だけ行えばよい。

1. branch
    * コマンド
        ```
        git branch [ブランチ名]     # ブランチを作成
        git switch [ブランチ名]     # ブランチを切り替え
        git switch -c [ブランチ名]  # 作成と切り替えを同時に行う
        git branch                  # 現在のブランチ一覧を表示
        ```
    * 使い方
        新しい機能を追加したり修正作業を行う際は、mainブランチから新しいブランチを作って作業する。
        作業が終わったらmainブランチにmergeする。
    * 概要
        ブランチとは作業の分岐点。mainブランチに影響を与えずに新機能の開発や実験ができる。
        複数人での作業では、各自がブランチを切って作業し後からまとめるのが基本的な流れ。

1. commit
    * コマンド
        ```
        git status                            # 現在の変更状態を確認
        git add [ファイル名]                  # 特定のファイルをステージング
        git add .                             # 変更したすべてのファイルをステージング
        git commit -m "変更内容のメッセージ"  # コミット
        ```
    * 使い方
        ファイルを変更した後、`git add`で変更をステージング（コミットの準備）し、`git commit`で確定する。
        メッセージには「何を変更したか」を簡潔に書く（例：「ログイン機能を追加」「〇〇のバグ修正」）。
    * 概要
        変更内容のスナップショットをローカルに保存すること。
        commitを積み重ねることで変更履歴となり、過去の状態に戻ることができる。

1. push
    * コマンド
        ```
        git push -u origin [ブランチ名]  # 初回
        git push                          # 2回目以降
        ```
    * 使い方
        commitした変更をGitHubに送信する。
        初回pushは `-u` オプションをつける。2回目以降は `git push` だけでよい。
        **organizationのリポジトリにpushする場合**は、事前に管理者から組織への招待を受けておく必要がある。
        招待後は通常のpushと同様に行えるが、初回はGitHubのログイン認証が求められる場合がある。
        その際はブラウザが自動で開くので、画面の指示に従ってログインすれば完了。
    * 概要
        ローカルのcommitをGitHubのリモートリポジトリに反映させること。
        pushすることで、他のメンバーが自分の変更を確認・利用できるようになる。

1. merge（Pull Request）
    * コマンド
        ```
        git switch main             # mainブランチに切り替え
        git merge [作業ブランチ名]  # 作業ブランチをmainに取り込む
        ```
    * 使い方
        作業ブランチでの作業が完了したら、mainブランチに切り替えてからmergeする。
        GitHubでは「**Pull Request（プルリクエスト）**」という機能を使ってmergeするのが一般的。
        Pull Requestを使うと他のメンバーがコードをレビューしてからmergeできるため、チーム開発では積極的に活用すること。
    * 概要
        別のブランチの変更を現在のブランチに取り込むこと。
        複数人の作業を一つにまとめる際に使う。
    * コンフリクト（競合）について
        複数人が同じファイルの同じ箇所を編集した場合、mergeの際に「コンフリクト」が発生することがある。
        その場合はgitが該当箇所を教えてくれるので、どちらの変更を採用するか手動で解決する必要がある。
        詳細はqiitaなどを参照すること。
